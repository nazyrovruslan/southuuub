Критично

P0

Прелоадер держит сайт, пока не скачаются все три видео

В коде прелоадера процент считается так: по 25% за каждое из трёх видео (main-video-banner, south-hub-video, snow-base-video) по доле buffered/duration и ещё 25% за JS/CSS. Сайт показывается только при 100% и ещё через 700 мс. Два из трёх видео находятся в середине страницы, но всё равно блокируют первый экран.

Таймаута нет. Если видео не буферизуется (режим энергосбережения на iPhone, экономия трафика, блокировщик, браузер без H.264), прелоадер висит бесконечно. Я воспроизвёл это: в тестовом Chromium без H.264 сайт застыл на 25% на всех разрешениях.

Важно

P1

Шапка наезжает на текст, и в закреплённой секции пустые полэкрана

На телефонах логотип и бургер в прозрачной шапке ложатся прямо на текст светлых блоков («строим тёплое сообщество…», «стать частью сообщества») и на цифру «669» в блоке статистики. В секции «где встречаемся» (GSAP pin) картинка занимает верх, а ниже на телефоне и планшете остаётся пустой чёрный экран; на 2560 px то же самое по горизонтали.

  • Шапке дать фон (полупрозрачный с backdrop-filter) при прокрутке над светлыми секциями или переключать цвет логотипа и добавить отступ сверху у секций, равный высоте шапки.
  • В закреплённой секции на <1024 px растягивать картинку на всю высоту, показывать подпись и кнопку под ней или отключать pin через ScrollTrigger.matchMedia.
P1

Фото галереи грузятся все сразу и в полном размере

14 фото society-*.jpg не помечены loading="lazy" и уходят в загрузку вместе с первым экраном, хотя галерея ниже середины страницы. srcset у них содержит один вариант w=1920 1x, поэтому телефон 360 px получает те же 1920×1280, что и десктоп. Фото проектов (встречи.webp и др.) имеют srcset 1080/1920 без sizes, на телефоне отдаётся 1080 px на блок 360 px.

  • В next/image указать sizes="100vw" (галерея) и sizes="(max-width:1024px) 100vw, 900px" (проекты): Next сам соберёт srcset 640/750/1080/1920.
  • Убрать priority/eager у галереи, оставить lazy.
  • Включить AVIF: images.formats: ['image/avif','image/webp'] в next.config; сейчас отдаётся только WebP.
P1

Ошибки в консоли

  • React #418 (hydration mismatch) при каждой загрузке на всех разрешениях: HTML с сервера не совпадает с первым рендером в браузере, и React перерисовывает дерево целиком. Частые причины: window/innerWidth, Date или случайные значения в рендере, условный рендер по ширине экрана.
  • «Failed to execute 'scrollTo' on 'Window'» из чанка с GSAP (65b56ee12b531693.js) на части разрешений: в scrollTo передаётся невалидное значение, вероятно NaN при пересчёте ScrollTrigger.
Собрать dev-сборку, посмотреть полный текст #418 и вынести зависящее от браузера в useEffect; в вызовах scrollTo проверять число.
P1

Анимации: что тяжело для браузера и что с доступностью

Используется GSAP + ScrollTrigger (pin, scrub) и CSS-анимации. Плавность прокрутки в тесте нормальная: 59 fps на десктопе; при замедлении CPU в 4 раза (имитация среднего телефона) ≈49–50 fps и 4 кадра дольше 50 мс за всю страницу. CLS при прокрутке 0,11 на 768 px (порог «хорошо» 0,1), на 1024 px 0,07, на остальных <0,01.

  • Ключевые кадры smoothFillTo* анимируют height, smoothMoveTo* анимируют bottom; есть transition: width/height до 3 с. Это пересчёт раскладки на каждом кадре.
  • will-change: top, bottom не помогает: эти свойства всё равно не композитятся.
  • Нет ни одного правила prefers-reduced-motion ни в CSS, ни в JS. Людям с вестибулярными нарушениями нельзя отключить параллакс и бегущие строки.
  • Бегущая строка (animation: scroll 60s) сделана на transform, это правильно.
  • Заменить height на transform: scaleY() с transform-origin: bottom, bottom на translateY.
  • Обернуть ScrollTrigger-анимации в gsap.matchMedia() с условием (prefers-reduced-motion: no-preference); в CSS остановить marquee под reduce.
  • CLS на планшете: задать фиксированную высоту блокам, которые меняют размер при входе в зону видимости.

Шрифты и JavaScript

Пять начертаний (IBM Plex Serif ×3, Mont ×2) подключены как TTF/OTF и предзагружаются все сразу: ≈395 КБ даже в gzip. JS главной: 1,17 МБ, 355 КБ в gzip. Самый крупный чанк 531 КБ (167 КБ gzip) содержит GSAP и antd с CSS-in-JS, хотя на странице из antd видны только кнопки (ant-btn); вывод по содержимому чанка.

  • Конвертировать в WOFF2 с подмножеством кириллица + латиница: ожидаемо ≈20–30 КБ на начертание, в сумме ≈100–150 КБ.
  • Предзагружать только 1–2 начертания, которые видны на первом экране.
  • Заменить antd Button на свою кнопку и убрать antd: это минус CSS-in-JS рантайм и ощутимая часть чанка.
  • Подключить только нужные плагины GSAP.

  • /speakers/ отдаёт первый байт за 6,2–6,9 с (три замера подряд), остальные страницы за 0,6–0,9 с. Это серверная генерация; нужен кэш или ISR.

P2

Удобство на телефоне

  • Зоны нажатия меньше рекомендованных 44×44 px: иконки соцсетей 24–30 px, кнопки «участвовать»/«да» 28 px в высоту, ссылки в футере 13–17 px.
  • Плашка cookies занимает ≈15% экрана телефона и висит до нажатия «да»; её можно сделать в одну строку.
  • Горизонтальной прокрутки нет ни на одном разрешении, но только потому, что у html и body стоит overflow: hidden: hero-видео, бегущая строка и блок статистики шире экрана (на 1920 px тело страницы 2760 px). Такая обрезка может ломать position: sticky; безопаснее overflow-x: clip на конкретных секциях.

Раздутый DOM

В HTML главной 487 тегов <img>: по 84 копии четырёх иконок в сетке «у нас много нового», 53 буквы «U», 33 логотипа и 32 иконки Telegram в бегущих строках. Всего 830–1220 элементов DOM в зависимости от ширины, HTML 176 КБ (15 КБ в gzip).

Декоративные сетки рисовать одним SVG-паттерном, CSS-фоном или canvas; бегущую строку строить из 2 копий контента, а не из десятков.
P2

SEO и тексты

  • Нет <h1>: «сообщество C-level в IT» сверстано как div.
  • Нет og:image: ссылка в Telegram и соцсетях будет без картинки.
  • В «кэмп-конференция для C-level в ІТ» буква «І» украинская (U+0406), «Т» кириллическая: поиск по «IT» это не найдёт.
  • Счётчик «1 лет комьюнити IT-руководителей»: нужно «1 год».
  • Опечатки в alt: «youtube chanell», «telegramm chanell».
  • Нет заголовков безопасности (HSTS, X-Content-Type-Options); сжатие только gzip, без brotli.
P2

Широкие экраны (2560 px)

Контент ограничен шириной ≈1920 px с серыми полями по бокам. Hero-видео исходно 1920 px, а показывается шириной до 2880 px, то есть растянуто в 1,5 раза. Мелкий текст навигации и подписей на таком экране читается плохо.

Для ≥2000 px отдавать 1440p-версию видео или ограничить его ширину; масштабировать типографику через clamp().

Что сделано хорошо

  • Статика и видео кэшируются на год (immutable), HTML, JS и CSS сжаты gzip.
  • Картинки отдаются через next/image в WebP, у всех заданы размеры.
  • Видео с muted playsinline, без звуковой дорожки, faststart.
  • Нет горизонтальной прокрутки ни на одном из 7 разрешений.
  • Сдвиги вёрстки при загрузке минимальны (CLS <0,01 до прокрутки).
  • Есть robots.txt, sitemap, canonical, description, разметка Organization.

Как проверялось

  • Headless Chromium (Playwright) на 360×740, 390×844, 768×1024, 1024×768 (как тач-устройства), 1366×768, 1920×1080, 2560×1440.
  • В тестовом Chromium нет H.264. Чтобы увидеть сайт после прелоадера, видео подменялись на копии в VP9 того же размера и битрейта, отдаваемые локально. Поэтому замер прелоадера (≈3,7 с) это нижняя граница без времени загрузки видео; время на сети в таблице посчитано.
  • Запросы шли через прокси облачного окружения, абсолютные времена ориентировочные.
  • Плавность: прокрутка колесом по всей странице, счёт кадров через requestAnimationFrame, CPU замедлен в 4 раза через DevTools Protocol. Программная отрисовка, на реальном телефоне цифры будут другими.
  • Видео разобраны ffprobe, CSS и JS скачаны и просмотрены вручную.
  • Не проверено на реальных устройствах. Стоит открыть сайт на iPhone в режиме энергосбережения: по коду прелоадер там может не уйти.
